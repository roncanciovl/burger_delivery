GitHub Classroom & Trabajo en Equipo

Por qué la mejor arquitectura colaborativa es un repositorio privado compartido por equipo (no un fork personal), cómo estructurar ramas individuales, proteger main con Rulesets y capturar el SHA de entrega para trazabilidad inmutable.

🏆 La Recomendación Principal de Arquitectura

En proyectos académicos de ingeniería y robótica con ROS 2, un repositorio privado compartido por equipo es ampliamente superior a que un estudiante haga un fork personal y añada a sus compañeros.

💡
El Principio de Igualdad y Control Institucional:

Con GitHub Classroom se crea una asignación grupal que genera automáticamente un repositorio compartido para cada equipo. Todos los integrantes quedan en absoluta igualdad de condiciones, el docente conserva acceso de administrador directo, y los permisos institucionales permanecen intactos ante cualquier eventualidad.

Criterio ✅ Repositorio Privado en GitHub Classroom ❌ Fork Propiedad de un Estudiante
Propiedad & Administración Pertenece a la Organización del curso administrada por el docente. Pertenece a la cuenta personal de un solo estudiante.
Igualdad del Equipo Todos los estudiantes tienen el mismo rol y permisos como colaboradores del equipo. Un estudiante es Owner con privilegios absolutos; los demás son invitados secundarios.
Retiros o Cambios de Grupo Si un integrante se retira o cambia de grupo, el repositorio no se pierde ni se bloquea. Si el dueño del fork cancela la materia o borra su cuenta, el equipo pierde todo el proyecto.
Reglas de Protección (Rulesets) El docente puede aplicar y forzar reglas de protección sobre main de forma centralizada. El estudiante dueño puede desactivar o eludir las protecciones cuando lo desee.
Auditoría & ABET Trazabilidad inmutable conservada en la nube institucional para acreditación académica. Se dificulta la conservación a largo plazo al depender de cuentas personales de alumnos.
Sincronización Estructura limpia con un solo remoto origin compartido. Requiere configurar y mantener remotos adicionales (upstream), aumentando la fricción.

🤝 Trabajo en Equipo Real

Emula el entorno de la industria de software y robótica: los desarrolladores colaboran en un repositorio corporativo común mediante ramas de features y revisiones cruzadas de código (Peer Reviews).

🎯 Evidencia ABET Transparente

Permite evaluar competencias de trabajo en equipo multidisciplinario, comunicación efectiva en PRs y rigor de ingeniería con registros verificables e históricos.

🔄 Flujo de Trabajo Recomendado

Sigue la secuencia desde la plantilla del docente hasta la integración de las ramas individuales de los estudiantes:

Paso 1: Preparación del Docente (Tag Inicial del Template)

El docente mantiene burger_delivery como base y etiqueta la versión con la que arranca el curso:

bash - Terminal Docente
git tag curso-2026-2-base
git push origin curso-2026-2-base

Paso 2: Creación de la Asignación Grupal en GitHub Classroom

En la interfaz de GitHub Classroom, el docente crea una Group Assignment seleccionando el repositorio base como Starter Code / Template. Classroom genera los repositorios privados con nombres estandarizados:

  • burger-delivery-equipo-01
  • burger-delivery-equipo-02
  • burger-delivery-equipo-03

Paso 3: Clonar el Repositorio de Equipo y Crear Rama Individual

Cada estudiante clona el mismo repositorio de su equipo, pero nunca trabaja directamente sobre main. Cada quien crea una rama semántica con su nombre y apellido:

bash - Terminal Estudiante
# Clonar el repo privado del equipo
git clone https://github.com/tu-organizacion/burger-delivery-equipo-01.git
cd burger-delivery-equipo-01

# Crear su rama individual según su responsabilidad asignada:
git checkout -b feat/estudiante-apellido-monitor
# o: git checkout -b feat/estudiante-apellido-launch
# o: git checkout -b fix/estudiante-apellido-diagnostics
# o: git checkout -b docs/estudiante-apellido-readme

Paso 4: Pull Request, Revisión Cruzada e Integración

Al terminar el desarrollo local, el estudiante sube su rama con git push origin feat/estudiante-apellido-monitor y abre un Pull Request hacia main. Otro integrante del equipo revisa el código línea por línea, deja comentarios o aprueba el PR antes de realizar el merge.

🛡️ Protección de la Rama main con GitHub Rulesets

Para evitar accidentes como sobrescribir código ajeno o subir código roto, la rama main debe estar estrictamente protegida. En GitHub esto se configura mediante Branch Protection Rules o la característica moderna GitHub Rulesets:

🚫
1. Prohibir Push Directo a main Restrict Pushes

Nadie (ni siquiera el líder del equipo) puede hacer git push origin main directamente. Todos los cambios deben pasar obligatoriamente por un Pull Request.

👥
2. Exigir Pull Request con Revisión de Otro Integrante Require 1 Approval

Un PR solo puede mergearse si al menos 1 compañero del equipo ha revisado el código y marcado "Approve". Fomenta la corresponsabilidad y el aprendizaje entre pares.

🤖
3. Exigir que Compile y Pasen las Pruebas (CI / Status Checks) Status Checks Pass

GitHub Actions ejecuta automáticamente colcon build y tests unitarios. Si el código no compila o los tests fallan, el botón de merge queda bloqueado en rojo.

🔒
4. Bloquear Force Push (git push --force) Block Force Pushes

Impide que alguien reescriba o borre commits del historial común. Garantiza la integridad del trabajo de todos los integrantes.

📜
5. Mantener Historial Visible y Trazable Require Linear History

Mantiene un gráfico de commits limpio, ordenado y auditable, fundamental para revisiones docentes y comités de acreditación.

📋 Entrega, Evaluación & Evidencia ABET

Para una evaluación rigurosa y auditable, en la fecha límite de entrega el equipo debe registrar información precisa que congele la versión exacta del sistema:

Dato de Entrega Descripción Ejemplo de Registro
1. URL del Repositorio Enlace al repo privado del equipo en la organización. https://github.com/curso-robotica/burger-delivery-equipo-01
2. Rama Evaluada Rama principal donde se integraron todos los PRs aprobados. main
3. SHA Exacto del Commit Hash hexadecimal de 40 caracteres que identifica de forma única e inmutable el estado del código. a1b2c3d4e5f67890abcdef1234567890abcdef12
4. Tag de Entrega Etiqueta semántica creada en el commit de entrega. corte1-entrega o entrega-final-2026
5. Integrantes & Roles Lista de estudiantes con sus usuarios de GitHub y módulos desarrollados. Estudiante 1 (@user1) - Monitor Nav2
6. PRs y Revisiones Lista de Pull Requests abiertos, revisados y fusionados con éxito. PR #1 (Merged), PR #2 (Merged), PR #3 (Merged)
🔐
¿Por qué registrar el SHA en Zubatronic / Plataforma de Evaluación?

El comando git rev-parse HEAD devuelve el identificador criptográfico exacto del último commit. Al registrar este SHA como localizador de evidencia, cualquier cambio o push posterior realizado por el equipo después de la fecha límite no alterará la versión evaluada. La evidencia permanece 100% inmutable.

bash - Obtener el SHA exacto y crear el Tag de entrega
# 1. Asegurarse de estar en main con los últimos cambios integrados:
git checkout main
git pull origin main

# 2. Obtener el SHA exacto de entrega:
git rev-parse HEAD
# Salida: 9f83b27e4a1c5d6e8b0f2a4c6e8d0f1a3b5c7e9a

# 3. Crear y subir el tag del corte:
git tag corte1-entrega
git push origin corte1-entrega
👤 Criterios para Evidencia Individual (Sin Caer en la Trampa de Contar Commits)

✅ Buenas Prácticas de Evidencia

  • Cuenta Propia: Cada estudiante debe usar exclusivamente su propia cuenta de GitHub.
  • Credenciales Intransferibles: Prohibido compartir credenciales o passwords.
  • Configuración Local Correcta: Configurar user.name y user.email antes de hacer commits.
  • Commits con Propósito: Mensajes descriptivos en su rama propia.
  • Revisión Cruzada Activa: Dejar comentarios técnicos en los Pull Requests de los pares.
  • Sustentación Personal: Explicar y defender el módulo desarrollado durante la demo con el robot.

⚠️ La Métrica Falsa: Número de Commits

El número de commits NO debe usarse como nota directa.

Los commits sirven para trazabilidad temporal, pero un estudiante podría hacer 50 commits de "arreglando typo" sin valor real. La calificación real debe sintetizar:

Calidad de Código + Pull Request + Code Review + Sustentación Oral + Funcionamiento en ROS 2
🏢 Alternativa: Sin GitHub Classroom (Organización + Template Repos)

Si la institución o el docente no utilizan la herramienta automatizada de GitHub Classroom, la segunda mejor opción sigue siendo mantener repositorios privados compartidos por equipo dentro de una Organización de GitHub:

📦 Procedimiento con Template Repositories

  1. Crear una Organización en GitHub para la asignatura (ej. github.com/robotica-unal-2026).
  2. Subir el repositorio base burger_delivery y marcarlo como Template Repository en sus Settings.
  3. Crear manualmente un repositorio privado por cada equipo desde la plantilla: burger-delivery-equipo-01, etc. (los repositorios creados desde plantilla inician con historial limpio e independiente).
  4. Invitar a los estudiantes de cada grupo como Collaborators con permisos de Escritura (Write).
  5. Configurar Rulesets para proteger la rama main.

❌ ¿Por qué el Fork Personal de un Estudiante NO es recomendable?

Técnicamente, un estudiante puede hacer un fork personal y sincronizarlo con el repositorio original mediante un remoto upstream (git remote add upstream ...). Sin embargo, en la práctica docente introduce serios problemas:

  • Pérdida de Gobernanza: La administración queda en la cuenta privada de un solo estudiante, no de la universidad.
  • Vulnerabilidad ante Cambios de Grupo o Retiros: Si el estudiante dueño del fork abandona el curso, sus compañeros quedan sin acceso a la administración del repo.
  • Permisos Asimétricos: El dueño del fork tiene permisos de superadministrador sobre sus compañeros, lo cual rompe la equidad del equipo.
  • Complicación de Remotos: Requiere que los estudiantes entiendan y gestionen la diferencia entre origin y upstream para no desincronizarse.
