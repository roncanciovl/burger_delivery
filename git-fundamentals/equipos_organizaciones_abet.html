GitHub Organizations & Trabajo en Equipo

Arquitectura profesional y sostenible: un repositorio privado compartido por equipo, ramas individuales feat/..., pull requests y una entrega identificada por commit SHA.

🏢

Arquitectura Nativa de GitHub Organizations & Gobernanza de Código

La metodología utiliza GitHub Organizations + repositorios de equipo con historia Git compartida + GitHub Teams. Los repositorios se siembran desde la historia del repositorio docente y no mediante Use this template, porque deben aceptar actualizaciones posteriores desde upstream.

🏆 La Recomendación Principal de Arquitectura

En proyectos colaborativos de ingeniería y robótica con ROS 2, un repositorio privado compartido por equipo dentro de una Organización de GitHub es la estrategia oficial y recomendada.

💡
El Principio de Igualdad y Gobernanza Institucional:

Los repositorios se crean dentro de la Organización de GitHub del curso y reciben la historia del repositorio docente. Los integrantes obtienen acceso mediante un GitHub Team, mientras el docente conserva la administración y la institución preserva el proyecto.

Criterio ✅ Repositorio de Equipo en Organización ❌ Fork Propiedad de un Estudiante
Propiedad & Administración Pertenece a la Organización institucional administrada por el docente. Pertenece a la cuenta personal de un solo estudiante.
Igualdad del Equipo Todos los estudiantes tienen el mismo rol y permisos como colaboradores del equipo. Un estudiante es Owner con privilegios absolutos; los demás son invitados secundarios.
Retiros o Cambios de Grupo Si un integrante cancela la materia o cambia de grupo, el repositorio no se pierde. Si el dueño del fork cancela la materia o borra su cuenta, el equipo pierde todo el proyecto.
Reglas de Protección (Rulesets) El docente aplica y fuerza reglas de protección sobre main de forma centralizada. El estudiante dueño puede desactivar o eludir las protecciones cuando lo desee.
Auditoría & ABET SO5 Historial preservado como evidencia complementaria del proceso académico. Se dificulta la conservación a largo plazo al depender de cuentas personales de alumnos.
Sincronización Git Estructura limpia con un solo remoto origin compartido para todo el equipo. Requiere configurar y sincronizar remotos cruzados (upstream), aumentando la fricción.

🤝 Trabajo en Equipo Industrial

Emula con total fidelidad el entorno empresarial: desarrolladores colaborando en repositorios corporativos comunes mediante ramas de features, Pull Requests y revisiones cruzadas de código (*Peer Reviews*).

🎯 Evidencia ABET Verificable

Facilita la evaluación de competencias de trabajo en equipo (*ABET SO5: Teamwork*), acuerdos de ingeniería y rigor técnico mediante commits individuales verificables.

🔄 Flujo de Trabajo Paso a Paso

Secuencia completa desde la base docente con historia compartida hasta la integración de ramas individuales:

Paso 1: Repositorio Base & Tag de Versión

El docente mantiene burger_delivery como repositorio base dentro de la organización y marca el punto de partida:

git tag curso-2026-2-base
git push origin curso-2026-2-base

Este tag no se mueve ni se reutiliza. Cada corrección se publica con un identificador nuevo.

Paso 2: Generación del Repo Privado de Equipo

Se crea un repositorio privado vacío y se envía la rama main desde la base docente, conservando la historia común:

  • burger-kinova-equipo-01
  • burger-kinova-equipo-02
  • burger-kinova-equipo-03

Visibilidad: Privado. Los estudiantes reciben Write mediante el GitHub Team correspondiente.

Paso 3: Ramas Individuales por Estudiante

Cada estudiante clona el repositorio del equipo y crea de inmediato su rama individual de trabajo:

git clone <URL-REPO-EQUIPO>
git checkout -b feat/estudiante-apellido-monitor

⛔ Regla: Queda estrictamente prohibido realizar commits directos en main.

Paso 4: Pull Request, Peer Review y Merge

Al terminar un módulo o hito:

  1. Hacer push de la rama individual: git push origin feat/...
  2. Abrir Pull Request hacia main.
  3. Revisión obligatoria por al menos 1 compañero de equipo.
  4. Merge a main tras aprobación.
🛡️ Reglas de Protección de Ramas (GitHub Rulesets)

Para garantizar la integridad del código y evitar que un estudiante sobrescriba accidentalmente la rama principal, se configuran Repository Rulesets en GitHub:

⚠️
Requisito del plan:

Los repositorios privados requieren GitHub Team o un beneficio educativo habilitado para aplicar Rulesets o protección de ramas. En GitHub Free estas reglas son política académica, pero GitHub no puede forzarlas.

⚙️ Configuración Paso a Paso en GitHub

  1. Entra a Settings del repositorio o de la Organización.
  2. En el menú lateral, selecciona Rules ➔ Rulesets.
  3. Haz clic en New ruleset ➔ New branch ruleset.
  4. Nombre: Proteccion-Main-Estudiantes.
  5. Enforcement status: Active.
  6. Target branches: Incluir Default branch (main).

📋 Reglas Obligatorias a Activar

☑ Restrict deletions

Impide que cualquier integrante borre la rama main.

☑ Block force pushes

Evita git push --force que destruya el historial del equipo.

☑ Require a pull request before merging

Exige al menos 1 aprobación de un compañero antes de fusionar.

📋 Protocolo de entrega y evidencia complementaria
⚠️
El commit SHA como referencia de evaluación:

En ingeniería no se evalúa "el estado actual de la rama main", porque un estudiante podría seguir modificando código después de la fecha límite. Cada equipo entrega el Hash SHA exacto del commit final y un Tag de versión.

🏷️ 1. Crear Tag y Obtener SHA

Al momento de la entrega en la rama main:

# Crear tag de entrega del corte
git tag -a entrega-2026-2-corte1 -m "Entrega oficial 2026-2 - corte 1"
git push origin entrega-2026-2-corte1

# Obtener el SHA de 40 caracteres inmutable
git rev-parse HEAD

Salida: 4f8b2d1c9a0e3f5b7c8d9e0f1a2b3c4d5e6f7a8b

🎯 2. Evidencia complementaria de trabajo en equipo

  • Distribución de Trabajo: Contribuciones técnicas visibles en ramas individuales y commits descriptivos.
  • Calidad de Revisiones: Comentarios técnicos y rigurosos en los Pull Requests (*Peer Review*).
  • Reproducibilidad: El código en el SHA de entrega compila limpiamente con colcon build sin errores.
  • Gobernanza: Respeto a las políticas de no push directo a main.
❌
Por qué NO evaluar por "Conteo Bruto de Commits":

El conteo de commits fomenta micro-commits sin valor técnico. El instrumento aprobado evalúa la relevancia técnica de los PR, la resolución de incidencias, la calidad del código integrado y la evidencia individual. GitHub no sustituye la rúbrica.

⚡ Automatización para Docentes con GitHub CLI (gh)

Los docentes pueden crear todos los repositorios de equipo en segundos utilizando el CLI oficial de GitHub (gh):

Script Bash: Crear repositorios conservando la historia Git
# 1. Autenticarse en GitHub
gh auth login

# 2. Definir organización y repositorio base
ORG="umng-mecatronica-ros"
BASE="git@github.com:roncanciovl/burger_delivery.git"

# 3. Crear repositorios vacíos y sembrar main desde la base
for i in $(seq -w 1 10); do
  REPO_NAME="burger-kinova-equipo-$i"
  echo "Creando $REPO_NAME en la organización $ORG..."
  gh repo create "$ORG/$REPO_NAME" --private
  git push "git@github.com:$ORG/$REPO_NAME.git" main:main
done
ℹ️
Resultado: Los diez repositorios comparten ancestros con la base docente y pueden integrar tags publicados desde upstream. Las ramas y protecciones se configuran después de la siembra.
